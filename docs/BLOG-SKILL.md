# 磐田物語ブログ（/blog/）編集方針と運用手順

このドキュメントは、`/blog/` に記事を書いて公開するための正本である。
毎日の自動生成をこの方針の上に載せる。スキル化するときはこの文書を材料にする。

---

## 0. 前提 ── このブログは何であって、何でないか

磐田物語は1,000ページを超える郷土史データベースであり、**正確さがサイトの価値そのもの**である。
本編の記事は、PDF・古写真・古地図・発掘調査報告・史料にあたって書かれ、学説が割れる場合は
断定せず併記し、生成後に査読パスを課している（`iwata-monogatari-academic-html` スキル）。

ブログはその本編とは役割が違う。**ブログは本編への案内役である。**

> **鉄則：ブログは新しい史実を主張しない。**
> 資料の裏付けなしに「〜だった」と書かない。史実そのものは本編の記事に書いてある。

自動生成が「もっともらしいが裏付けのない史実」を毎日書き足し始めると、サイト全体の信頼が
崩れる。それを防ぐことが、この方針と後述の品質ゲートの唯一の目的である。

---

## 1. 書いてよい枠（これ以外は書かない）

台帳 `data/blog-posts.json` の `kind` と対応する。

| kind | 内容 |
|---|---|
| `reading` | 既存ページの読み解き。このサイトの既存記事を紹介・関連づける |
| `now-and-then` | 現在の磐田の風景と、**既存ページに書かれている**過去との対比 |
| `how-to-research` | 資料の探し方、郷土史の調べ方 |
| `guide` | 地区・地名の由来など、**既存ページに既に書かれている内容**への導線 |

### 書いてはいけないこと

- 既存ページに書かれていない史実を、新たに述べること
- 出典を示さずに年代・人物・出来事を断定すること
- 学説が割れている論点について、一方だけを採って断定すること（本編同様、併記する）
- 既存500ページ超の内容と重複する記事を、新規記事として立てること
- 公的機関以外の外部サイトを根拠として引くこと

### 断定を避ける

「〜と考えられる」「〜と記録されている」「〜とされる」を使う。
出典（サイト内の既存ページ、または公的機関）を必ず明示する。
**年号を含む文を書くときは、必ずその段落に出典リンクを置く**（機械的に検査される。§4 G10）。

## 2. ファイル構成

| 対象 | 場所 |
|---|---|
| 台帳（正本） | `data/blog-posts.json` |
| 記事の実体 | `blog/<slug>/index.html` |
| 一覧（自動生成） | `blog/index.html` ← 手で編集しない |
| 生成・検査スクリプト | `scripts/build_blog.py` |
| 専用CSS | `assets/css/blog.css` |
| sitemap の該当区画 | `sitemap.xml` の `<!-- blog:start -->`〜`<!-- blog:end -->` ← 手で編集しない |

`slug` は `YYYYMMDD-英小文字ハイフン` 形式。URLは `/blog/<slug>/`（末尾スラッシュ）。

---

## 3. 記事を1本書いて公開するまでの手順

```powershell
# 0. 【例外なし】まず本番との一致を確認する。失敗したら作業を止めて原因を調べる
npm.cmd run check-live-sync

# 1. 重複チェック：既存ページと同じ話題を新規に立てない
#    data/pages.json の title/summary と、書こうとしている主題を突き合わせる

# 2. 記事を書く： blog/<slug>/index.html
#    既存記事（例 c167.html）ではなく、既存のブログ記事をテンプレートにする

# 3. 台帳に追記： data/blog-posts.json の posts[] に1件足す

# 4. 検査＋生成（品質ゲートを通らなければ一覧は生成されない）
python scripts/build_blog.py

# 5. サイト側の整合（ブログは新着フィードに載らないので通常は差分なし）
npm.cmd run build
npm.cmd run knowledge-count

# 6. 公開直前
npm.cmd run release:stamp   # 台帳を変更したので再スタンプが要る
npm.cmd run guard
git add <更新ファイル>
git commit -m "..."
git push                    # Cloudflare Pages が自動でビルド・デプロイする
```

`wrangler pages deploy` はこのマシンでは実行できない（意図的に権限を外してある）。
公開は `git push` のみ。詳細は `README.md`。

### 記事HTMLの必須要素

`scripts/build_blog.py` が機械的に要求する。欠けると一覧が生成されない。

- `<div class="post-body">` … `<!-- /post-body -->` で囲まれた本文（1,200〜9,000字）
- `<p class="post-scope">` … この記事が新しい史実を主張しないことの明示
- `<span class="post-author">` … 著者表記
- `<section class="post-sources">` … 出典（`<li>` 2件以上）
- `canonical` と `og:url` が `https://iwata-monogatari.net/blog/<slug>/` に一致
- **サイト内の既存ページへのリンク2本以上**
- `<meta name="iwata:published">` `<meta name="iwata:new-article">` `<meta property="article:published_time">` を**持たせない**
  （持たせると `sync_new_articles.py` の新着自動収集に混入する）

## 4. 「新しい史実を主張しない」を機械で担保する仕組み

`python scripts/build_blog.py` が全記事に対して次を検査し、1件でも落ちれば
`/blog/index.html` を生成せず exit 1 で止まる。**自動生成運用の歯止めはここである。**

| # | ゲート | 何を防ぐか |
|---|---|---|
| G5 | **サイト内の既存ページへのリンクが2本以上**（`data/pages.json`／地区ポータルに登録済みのURLに限る） | 記事の骨格を「既に書かれていること」に縛る。既存ページを指せない話題は守備範囲外 |
| G10 | **年号（西暦・元号）を含む段落には、必ず `<a>` リンクがあること** | 「〇〇年に△△だった」という新規の史実主張を、出典なしには書けなくする |
| G7 | 外部リンクは公的機関等の許可ドメインのみ（`*.go.jp` `*.lg.jp` `*.ac.jp` `city.iwata.shizuoka.jp` ほか） | 素性の知れない外部ページを根拠に仕立てさせない |
| G9 | 禁止表現（`新事実` `新発見` `独自調査により` `断定できる` `間違いなく` `に違いない` `定説を覆す` ほか）を含まない | 断定・新発見の主張そのものを禁じる |
| G3 | 内部リンクがリポジトリに実在すること | デッドリンク・存在しないページの捏造を防ぐ |
| G15 | タイトルが既存1,000超ページおよび他ブログ記事と重複しないこと | 既存記事と紛らわしい重複記事を防ぐ |
| G11 | `<p class="post-scope">` が存在すること | 読者にも「ここでは新史実を主張しない」と明示させる |
| G16 | 新着収集用の `meta` を持たないこと | 本編の新着フィードを汚さない |

ほかに、本文分量（G2）、出典2件以上（G8）、canonical/og:url一致（G13）、
公開日と台帳の一致（G14）、著者表記（G12）、台帳の必須項目（G0）を検査する。

**機械で判定できないこと**：本文の内容が本当に既存ページの範囲内かどうか。
最終判断は執筆者・査読者が行う。ゲートは下限であって、合格＝良い記事ではない。

### 本編の品質検査との関係

本編用の `check_heading_density.py` / `check_content_quality.py` /
`check_objective_quality.py` は `count_as_knowledge: true` のページだけを見る。
ブログは `/blog/` を `count_as_knowledge: false` で `data/pages.json` に登録して
あるため、本編用の検査（最低1,800字・図版必須など）の対象外であり、
「磐田の集合知（公開記事数）」の数字にも算入されない。ブログ側の品質は
`scripts/build_blog.py` が単独で担保する。

## 5. サイトへの接続状況

- ヘッダーナビ … `partials/header.html`（配信時に全ページへ差し込まれる）に「ブログ」を追加済み。
  `index.html` 内のフォールバック用ナビにも同じ項目を追加してある。
- トップページ … 「磐田物語の入口」セクションに `ブログを読む` カードを追加済み。
- `data/pages.json` … `/blog/` を1件登録（`count_as_knowledge: false`、
  `show_in_updates: false`、`show_in_all_articles: false`）。個々の記事は登録しない。
- `sitemap.xml` … `<!-- blog:start -->`〜`<!-- blog:end -->` を
  `scripts/build_blog.py` が毎回上書きする。区画の外には触れない。
- `data/new-articles.json` / `updates.html` / `c034.html` … **ブログは載せない**。
  本編記事の新着だけを扱う場所である。`sync_new_articles.py` の `SKIP_DIRS` に
  `blog` を追加して機械的に保証してある。

---

## 6. 自動生成運用にするときの注意

1. 毎朝の生成は「台帳へ1件追記 → 記事HTML生成 → `python scripts/build_blog.py`」。
   **ゲートに落ちたら公開せず、その日は記事なしで終える**（無理に通そうとして
   出典を捏造させない）。
2. 題材は既存ページから選ぶ。`data/pages.json` の `summary` と `topics` を
   題材の供給源にすると、自然と「既存ページの読み解き」の枠に収まる。
3. 同じ既存ページばかり紹介しないよう、直近に取り上げた `internal_links` を
   台帳から参照して分散させる。
4. `npm.cmd run check-live-sync` が通らない日は、記事を書かず人に報告する。
